# Fornach-engine Specification

> Generated by openlore v1.2.0 on 2026-10-07 14:42

## Purpose

Calculates tactical timing thresholds and evaluates Indes tempo-seizure opportunities for combatants
reacting in the Nach.

## Requirements

> `src/Fornach.Engine/IndesResolver.fs`

### Requirement: CalculateThreshold

The system SHALL calculate the threshold of net defense hits required to seize the vor from the nach, reducing the requirement by 1 when the defender has an active parrying buckler preparation.

#### Scenario: BaselineThresholdCalculation
- **GIVEN** A combatant without a Parrying Buckler preparation
- **WHEN** calculateThreshold is invoked
- **THEN** The default threshold of 3 is returned

#### Scenario: ThresholdReductionWithParryingBuckler
- **GIVEN** A combatant with an active Parrying Buckler preparation
- **WHEN** calculateThreshold is invoked
- **THEN** The threshold is reduced by 1 to 2, widening the tempo-seizure window

### Requirement: EvaluateIndes

The system SHALL determine whether a defender in the nach successfully seizes the vor by comparing net defense hits against the calculated threshold.

#### Scenario: SuccessfulVorSeizure
<!-- openlore-test: tags=smoke (auto) -->
- **GIVEN** A defender whose margin of defense hits minus attack hits is greater than or equal to the threshold
- **WHEN** evaluateIndes is evaluated
- **THEN** An IndesEvaluation with CanSeizeVor set to true is returned along with the threshold and hit margins

#### Scenario: InsufficientMarginFailsToSeizeVor
<!-- openlore-test: tags=regression (auto) -->
- **GIVEN** A defender whose net defense hits fall below the calculated threshold
- **WHEN** evaluateIndes is evaluated
- **THEN** An IndesEvaluation with CanSeizeVor set to false is returned

> `src/Fornach.Engine/IndesResolver.fs`

### Requirement: ResolveConcealedBlade

The system SHALL interrupt an incoming attack from the nach with a quick-draw puncture, apply physical damage and overwhelm, consume the concealed blade preparation, and reset the attacker's combo if disrupted.

#### Scenario: AttackDisruptedByOverwhelmingFinesseDisparity
- **GIVEN** A defender possessing an active Concealed Blade preparation whose Finesse is at least 1.6 times the
attacker's Reflex
- **WHEN** resolveConcealedBlade is resolved
- **THEN** Attacker takes puncture damage, Concealed Blade is consumed, the attacker's combo tracker is reset,
and disruption is flagged as true

#### Scenario: CounterPunctureWithoutDisruption
- **GIVEN** An attacker with sufficient Reflex to resist full interruption and health remaining after puncture
damage
- **WHEN** resolveConcealedBlade is resolved
- **THEN** Attacker suffers damage and overwhelm increase, Concealed Blade is removed from defender, combo is
preserved, and disruption is flagged as false

### Requirement: ResolveIndesOpportunity

The system SHALL assess contest results and execute an indes tempo seizure, granting study stacks to the defender, increasing attacker frustration, resetting attacker combo momentum, and emitting combat events when the threshold is met.

#### Scenario: DefenderSuccessfullyArrestsMomentumAndSeizesTheVor
<!-- openlore-test: tags=smoke (auto) -->
- **GIVEN** A contest where defender net hits satisfy the Indes evaluation threshold
- **WHEN** resolveIndesOpportunity is resolved
- **THEN** Defender gains 1 Study stack, attacker gains 10 Frustration, attacker combo is reset, IndesSeized
and ComboReset events are emitted, and success returns true

#### Scenario: ContestHitsDoNotMeetIndesThreshold
<!-- openlore-test: tags=smoke (auto) -->
- **GIVEN** A contest where defender net hits do not satisfy the Indes evaluation threshold
- **WHEN** resolveIndesOpportunity is resolved
- **THEN** Both combatants remain unmodified, an empty event list is returned, and success returns false

> `src/Fornach.Engine/TowerSession.fs`

### Requirement: UpdateFov

The system SHALL recalculates player vision cone and field-of-view, updating visible tiles and explored floor memory.

#### Scenario: RecalculateFOVAndUpdateExploredTiles
- **GIVEN** An active tower run state with player position, facing direction, and locomotion
- **WHEN** updateFov is called
- **THEN** The player field-of-view is computed via VisionResolver and Fov, visible tiles are refreshed, and
explored tiles are unioned into the current floor state

### Requirement: CompleteQuest

The system SHALL marks a specified quest as completed on the floor, unlocks the ascension portal, and updates player completed quests.

#### Scenario: CompleteActiveQuest
- **GIVEN** A valid questId matching an active quest on the floor
- **WHEN** completeQuest is called
- **THEN** The quest is marked as completed, the stairway portal is unlocked, the quest ID is added to
CompletedQuests, and an ascension portal unlock message is logged

### Requirement: InitSessionWithMode

The system SHALL initializes a new tower dungeon ascent session at a specified floor with designated story mode, generating the initial floor and fov.

#### Scenario: InitializeSessionWithStoryModeFlag
- **GIVEN** A player combatant, seed, starting floor number, and story mode boolean flag
- **WHEN** initSessionWithMode is called
- **THEN** A new TowerRunState is constructed with generated floor data at the spawn location, initial items,
log entry, and computed FOV

### Requirement: InitSession

The system SHALL initializes a standard non-story tower dungeon ascent session starting at a given floor.

#### Scenario: InitializeStandardSession
<!-- openlore-test: tags=smoke (auto) -->
- **GIVEN** A player combatant, seed, and starting floor number
- **WHEN** initSession is called
- **THEN** A new TowerRunState is created with isStoryMode set to false

### Requirement: AscendFloor

The system SHALL advances the run to the next floor via the stairway door, resetting status meters and generating new floor layout.

#### Scenario: AscendToNextFloor
- **GIVEN** An active tower run state at the current floor
- **WHEN** ascendFloor is called
- **THEN** The floor number increments by 1, a new floor is generated, player status meters reset to zero,
player moves to spawn location facing North, and FOV is recalculated

### Requirement: StepPlayer

The system SHALL resolves a single turn of player movement or interaction in a target direction, emitting discrete dungeon events.

#### Scenario: BlockedByUnwalkableTile
- **GIVEN** The target tile in direction dir is not walkable (e.g., Chasm or Pillar)
- **WHEN** stepPlayer is called
- **THEN** Player facing is updated, a blocked path message is logged, and no events are emitted

#### Scenario: EncounterUndefeatedEnemy
- **GIVEN** The target position contains an undefeated TowerEnemy
- **WHEN** stepPlayer is called
- **THEN** A CombatTriggered event is emitted and encounter message is added to the log

#### Scenario: InteractWithNPCCompletingQuest
- **GIVEN** The target position contains an NPC with an active quest, reward not yet given, and at least one
enemy defeated
- **WHEN** stepPlayer is called
- **THEN** The quest is completed, stairway unlocked, morale and souls awarded, NpcInteracted event emitted,
and completion message logged

#### Scenario: InteractWithNPCWithoutCompletingQuest
<!-- openlore-test: tags=smoke (auto) -->
- **GIVEN** The target position contains an NPC without quest completion conditions met
- **WHEN** stepPlayer is called
- **THEN** An NpcInteracted event is emitted with quest accepted flag and NPC dialogue is logged

## Technical Notes

- **Dependencies**: Indes, TowerGenerator, VisionResolver, Fov
