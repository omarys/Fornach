# Architecture Specification

> Generated by openlore v1.2.0 on 2026-10-07 14:42

## Purpose

This document describes the architectural patterns and structure of the system.

## Architecture Style

Layered architecture divided into discrete domain modules (CLI presentation, gameplay engine,
spatial computations, narrative runner, and core domain entities), separating spatial mathematics
and combat resolution from session coordination.

## Requirements

### Requirement: LayeredArchitecture

The system SHALL maintain separation between:
- CLI & Presentation (fornach-cli) (Terminal interaction, visual rendering, and death animation sequences for the player.)
- Engine & Simulation (fornach-engine) (Tower session lifecycle management, combat simulation orchestration, tactical assessments, and equipment trigger resolution.)
- Spatial & Navigation (fornach-spatial) (2D grid operations, Bresenham line tracing, directional line-of-sight/field-of-view shadowcasting, and A* pathfinding.)
- Narrative (fornach-story) (Interactive story progression coordination, branching knot navigation, and memory unlocking.)
- Domain Models (fornach-domain) (Core entity schemas, floor aggregates, combatant archetypes, and simulation result metrics.)

#### Scenario: LayerSeparation
- **GIVEN** a request from the presentation layer
- **WHEN** business logic is needed
- **THEN** the presentation layer delegates to the business layer
- **AND** direct database access from presentation is prohibited

### Requirement: SecurityModel

The system SHALL implement security via: None evident; the system functions as a local, standalone terminal-based application without network endpoints, user authentication, or access control policies.

#### Scenario: AuthenticatedAccess
- **GIVEN** an unauthenticated request
- **WHEN** accessing protected resources
- **THEN** access is denied

## Layer Structure

### CLI & Presentation (fornach-cli)

**Purpose**: Terminal interaction, visual rendering, and death animation sequences for the player.
**Location**: `fornach-cli, DeathAnimation`

### Engine & Simulation (fornach-engine)

**Purpose**: Tower session lifecycle management, combat simulation orchestration, tactical assessments, and equipment trigger resolution.
**Location**: `TowerSession, TacticalAssessment, EquipmentTriggerService, IndesResolver, Indes, MeterManagement, ResourcePool, CombatIdentifierService, FloorThemeService`

### Spatial & Navigation (fornach-spatial)

**Purpose**: 2D grid operations, Bresenham line tracing, directional line-of-sight/field-of-view shadowcasting, and A* pathfinding.
**Location**: `Pathfinding, Fov, Los, Line, Point, VisionCone, VisionResolver`

### Narrative (fornach-story)

**Purpose**: Interactive story progression coordination, branching knot navigation, and memory unlocking.
**Location**: `StoryRunner, NarrativeState, StoryMemory, MemoryEchoData`

### Domain Models (fornach-domain)

**Purpose**: Core entity schemas, floor aggregates, combatant archetypes, and simulation result metrics.
**Location**: `TowerFloor, TowerEnemy, TowerNpc, TowerChest, TowerShrine, AltarChoice, ArchetypeInfo, SingleCombatResult, SimulationSummary, GroupSimulationSummary`

## Data Flow

User actions enter via CLI → TowerSession coordinates turn updates → spatial queries (Pathfinding,
Fov, VisionResolver) update entity visibility and positions on TowerFloor → combat encounters
trigger combat services (IndesResolver, MeterManagement, ResourcePool) and generate combat results →
StoryRunner routes narrative events into NarrativeState → game state is rendered back to the
terminal (no external persistence layer is evidenced).
