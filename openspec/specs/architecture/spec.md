# Architecture Specification

> Generated by openlore v1.2.0 on 2026-11-13 21:11

## Purpose

This document describes the architectural patterns and structure of the system.

## Architecture Style

Layered domain-driven architecture. The codebase is organized into separated layers across distinct
domain packages: core business rules and entities (fornach-domain), simulation orchestration and
procedural generation (fornach-engine), mathematical spatial computations (fornach-spatial), and
documentation knowledge extraction with browser-based graph visualization (openwiki,
openwiki-visualizer).

## Requirements

### Requirement: LayeredArchitecture

The system SHALL maintain separation between:
- Domain Layer (fornach-domain) (Encapsulates core game entities, character stats, classes, equipment, meters, and immutable combatant domain logic.)
- Engine & Simulation Layer (fornach-engine) (Orchestrates turn loops, tactical resolution, dice evaluations, AI behavior, dungeon procedural generation, and batch headless simulations.)
- Spatial & Geometric Layer (fornach-spatial) (Provides 2D grid math, discrete raytracing, field of view, line of sight, and obstacle-aware pathfinding routines.)
- Knowledge Management Layer (openwiki) (Parses repository documentation and frontmatter, constructs in-memory graph models, and automates wiki synchronization.)
- Visualization & Presentation Layer (openwiki-visualizer) (Hosts local HTTP/SSE services, generates static bundles, and renders interactive force-directed graph UI in the browser.)

#### Scenario: LayerSeparation
- **GIVEN** a request from the presentation layer
- **WHEN** business logic is needed
- **THEN** the presentation layer delegates to the business layer
- **AND** direct database access from presentation is prohibited

### Requirement: SecurityModel

The system SHALL implement security via: No explicit authentication, authorization, or access control mechanisms are present in the provided analysis data; the engine and visualizer operate locally and offline with direct filesystem and in-memory access.

#### Scenario: AuthenticatedAccess
- **GIVEN** an unauthenticated request
- **WHEN** accessing protected resources
- **THEN** access is denied

## Layer Structure

### Domain Layer (fornach-domain)

**Purpose**: Encapsulates core game entities, character stats, classes, equipment, meters, and immutable combatant domain logic.
**Location**: `Combatant, StatBlock, Attributes, Bestiary, Equipment, Consumables, ArmorIntegrity, Meters, TowerModel`

### Engine & Simulation Layer (fornach-engine)

**Purpose**: Orchestrates turn loops, tactical resolution, dice evaluations, AI behavior, dungeon procedural generation, and batch headless simulations.
**Location**: `ActionResolver, CombatSimulation, AI, DicePool, TowerGenerator, TowerSession, CombatEventService, CombatLogger`

### Spatial & Geometric Layer (fornach-spatial)

**Purpose**: Provides 2D grid math, discrete raytracing, field of view, line of sight, and obstacle-aware pathfinding routines.
**Location**: `Pathfinding, Fov, Los, Dijkstra, Line, Distance, Direction, Point, VisionCone`

### Knowledge Management Layer (openwiki)

**Purpose**: Parses repository documentation and frontmatter, constructs in-memory graph models, and automates wiki synchronization.
**Location**: `WikiGraphBuilderService, PageManifestService, WikiUpdateService, OpenWikiUpdateWorkflow`

### Visualization & Presentation Layer (openwiki-visualizer)

**Purpose**: Hosts local HTTP/SSE services, generates static bundles, and renders interactive force-directed graph UI in the browser.
**Location**: `VisualizerServerService, StaticVisualizerExportService, OpenWikiVisualizerClient, docs/openwiki-visualizer/client.js`

## Data Flow

In the game simulation, inputs flow from TowerSession and TowerGenerator through spatial grid
computations (fornach-spatial), feeding tactical evaluations and AI decisions into ActionResolver
and DicePool, which emit domain events via CombatEventService and state logs via CombatLogger. In
the documentation subsystem, Markdown files are parsed by WikiGraphBuilderService into Node and Link
entities, served by VisualizerServerService or compiled by StaticVisualizerExportService, and
rendered in client.js via force-directed canvas layout and Server-Sent Events.
