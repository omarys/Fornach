# Architecture Specification

> Generated by openlore v1.2.0 on 2026-10-19 15:43

## Purpose

This document describes the architectural patterns and structure of the system.

## Architecture Style

Layered and modular domain-driven architecture. The codebase is organized into distinct domain
layers separating CLI terminal presentation, game session and simulation orchestration, spatial
geometry/pathfinding algorithms, core combat rules/entities, narrative execution, and an auxiliary
web-based documentation visualizer.

## Requirements

### Requirement: LayeredArchitecture

The system SHALL maintain separation between:
- Presentation / CLI (fornach-cli) (Coordinates CLI entry points, argument parsing, interactive terminal menus, Dracula-themed Spectre.Console UI rendering, viewport calculations, and ASCII animations.)
- Story & Narrative (fornach-story) (Manages interactive narrative progression, Ink story engine script execution, choice branching, and narrative boss encounter generation.)
- Game Engine & Simulation (fornach-engine) (Encapsulates turn-based combat resolution, opposed dice pool contests, tactical tempo (Indes) evaluation, procedural tower floor generation, session state, and headless Monte Carlo balance simulations.)
- Spatial & Pathfinding (fornach-spatial) (Provides 2D grid primitives, Bresenham line tracing, recursive shadowcasting field-of-view, vision cone containment, and A*/Dijkstra pathfinding algorithms.)
- Core Domain (fornach-domain) (Defines core game entities, character archetypes, bounded entropy meters, resource pools, equipment hooks/triggers, and progression scaling rules.)
- Documentation & Visualization (openwiki / openwiki-visualizer) (Provides client-side interactive force-directed graph visualization, Markdown document reading, and Server-Sent Events (SSE) live-reload synchronization.)

#### Scenario: LayerSeparation
- **GIVEN** a request from the presentation layer
- **WHEN** business logic is needed
- **THEN** the presentation layer delegates to the business layer
- **AND** direct database access from presentation is prohibited

### Requirement: SecurityModel

The system SHALL implement security via: No authentication or authorization mechanisms are evident in the codebase. The game engine operates as a standalone, single-user CLI application with local disk access. Security measures are limited to the client-side documentation visualizer (VisualizerLib/ClientLib), which applies HTML escaping and path normalization to prevent injection and traversal vulnerabilities when parsing Markdown and graph paths.

#### Scenario: AuthenticatedAccess
- **GIVEN** an unauthenticated request
- **WHEN** accessing protected resources
- **THEN** access is denied

## Layer Structure

### Presentation / CLI (fornach-cli)

**Purpose**: Coordinates CLI entry points, argument parsing, interactive terminal menus, Dracula-themed Spectre.Console UI rendering, viewport calculations, and ASCII animations.
**Location**: `Program, Display, TowerDisplay, Theme, DeathAnimation, EnvironmentScenes`

### Story & Narrative (fornach-story)

**Purpose**: Manages interactive narrative progression, Ink story engine script execution, choice branching, and narrative boss encounter generation.
**Location**: `StoryRunner, StoryBosses, NarrativeState, StoryMemory`

### Game Engine & Simulation (fornach-engine)

**Purpose**: Encapsulates turn-based combat resolution, opposed dice pool contests, tactical tempo (Indes) evaluation, procedural tower floor generation, session state, and headless Monte Carlo balance simulations.
**Location**: `ActionResolver, ActionService, AttackEstimator, CombatEventService, CombatLogger, DicePool, IndesResolver, RuntimeLog, Simulation, TowerGenerator, TowerSession, WorldEvents`

### Spatial & Pathfinding (fornach-spatial)

**Purpose**: Provides 2D grid primitives, Bresenham line tracing, recursive shadowcasting field-of-view, vision cone containment, and A*/Dijkstra pathfinding algorithms.
**Location**: `Dijkstra, Direction, Distance, FovService, LineService, LosService, Pathfinding, Point, VisionCone, VisionResolver`

### Core Domain (fornach-domain)

**Purpose**: Defines core game entities, character archetypes, bounded entropy meters, resource pools, equipment hooks/triggers, and progression scaling rules.
**Location**: `Archetypes, Bestiary, CharacterClass, CollapseState, Combatant, Equipment, EquipmentTriggerService, Meters, Pool, ProgressionScale, TacticalAssessment, TierFactory, TowerFloor, WeaponCondition`

### Documentation & Visualization (openwiki / openwiki-visualizer)

**Purpose**: Provides client-side interactive force-directed graph visualization, Markdown document reading, and Server-Sent Events (SSE) live-reload synchronization.
**Location**: `OpenWikiVisualizerClient, VisualizerClient, VisualizerClientLib, VisualizerLib, ClientLib`

## Data Flow

User inputs or CLI arguments enter through Program → TowerSession or StoryRunner initiates the run,
calling TowerGenerator to create procedural TowerFloor instances → Spatial services (FOV,
Pathfinding, Line-of-Sight) calculate visibility and entity movement per turn → Combat actions route
through ActionService and ActionResolver, rolling DicePool contests, triggering equipment hooks, and
updating Combatant resource pools/meters → CombatEventService emits domain events and results are
rendered to the terminal via TowerDisplay/Display (Spectre.Console) → Detailed encounter summaries
and debug traces are persisted directly to disk files via CombatLogger and RuntimeLog. (Separately,
OpenWiki documentation graphs are synchronized via GitHub Actions and live-streamed to client.js
over SSE).
